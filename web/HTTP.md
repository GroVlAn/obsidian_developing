
**HTTP** — это гипертекстовый протокол передачи данных прикладного уровня в сетевой модели OSI.

Главная особенность HTTP — представление всех данных в нём в виде простого текста. Через HTTP разные узлы в сети общаются между собой. Модель клиент-серверного взаимодействия классическая: клиент посылает запрос серверу, сервер обрабатывает запрос и возвращает ответ клиенту. Полученный ответ клиент обрабатывает и решает: прекратить взаимодействие или продолжить отправлять запросы.

**HTTPS (HTTP _Secure_**) — это надстройка над протоколом HTTP, которая поддерживает шифрование посредством криптографических протоколов SSL и TLS. Они шифруют отправляемые данные на клиенте и дешифруют их на сервере. Это защищает данные от чтения злоумышленниками, даже если им удастся их перехватить.
### Статусы ответов
- Информационные ответы: коды 100–199
    
- Успешные ответы: коды 200–299
    
- Редиректы: коды 300–399
    
- Клиентские ошибки: коды 400–499
    
- Серверные ошибки: коды 500–599

#### Информационные ответы
**100 Continue** — промежуточный ответ. Он указывает, что запрос успешно принят.
**101 Switching Protocol** присылается в ответ на запрос, в котором есть заголовок _Upgrade_. Это означает, что сервер переключился на протокол, который был указан в заголовке. Такая методика используется, например, для переключения на протокол _Websocket_.
**102 Processing** — запрос получен сервером, но его обработка ещё не завершена.

#### Успешные ответы
**200 OK** — запрос принят и корректно обработан веб-сервером.
**201 Created** — запрос корректно обработан и в результате был создан новый ресурс. Обычно он присылается в ответ на POST запрос.
**202 Accepted** — Запрос получен, но еще не обработан. Это «уклончивый» ответ, поскольку в HTTP нет возможности позже отправить асинхронный ответ с результатом обработки запроса. Этот код предназначен для случаев, когда запрос обрабатывается другим процессом или сервером, а также для пакетной обработки.
**203 Non-Authoritative Information** — Возвращенные метаданные не полностью совпадают с теми, которые доступны на исходном сервере, а получены из другого источника. Чаще всего это используется для зеркал или резервных копий ресурсов. За исключением таких случаев предпочтительнее использовать ответ `200 OK`.
**204 No Content** — Для этого запроса нет содержимого для отправки, но заголовки ответа могут быть полезны. Пользовательский агент может использовать их для обновления закешированных заголовков, полученных ранее для этого ресурса.

#### Редиректы
**301 Moved Permanently** — запрашиваемый ресурс на постоянной основе переехал на новый адрес. Тогда новый путь к ресурсу указывается сервером в заголовке `Location` ответа.
**302 Found** — указывает, что целевой ресурс временно доступен по другому URl. Адрес перенаправления может быть изменен в любое время, а клиент должен продолжать использовать действующий URI для будущих запросов. Тогда временный путь к ресурсу указывается сервером в заголовке `Location` ответа.
**307 Temporary Redirect** — имеет то же значение, что и код 302, за исключением того, что клиент не может менять метод последующего запроса.
**308 Permanent Redirect** — имеет то же значение, что и код 301, за исключением того, что клиент не может менять метод последующего запроса.

#### Клиентские ошибки
**400 Bad Request** — запрос от клиента к веб-серверу составлен некорректно. Обычно это происходит, если клиент не передаёт необходимые заголовки или параметры.
**401 Unauthorized** — получение запрашиваемого ресурса доступно только аутентифицированным пользователям.
**403 Forbidden** — у клиента не хватает прав для получения запрашиваемого ресурса. Например, когда обычный пользователь сайта пытается получить доступ к панели администратора.
**404 Not Found** — сервер не смог найти запрашиваемый ресурс.
**405 Method Not Allowed** — сервер знает о существовании HTTP-метода, который был указан в запросе, но не поддерживает его. В таком случае сервер должен вернуть список поддерживаемых методов в заголовке `Allow` ответа.
**409 Conflict** — Запрос конфликтует с текущим состоянием сервера.

#### Серверные ошибки
**500 Internal Server Error** — на сервере произошла непредвиденная ошибка.
**501 Not Implemented** — метод запроса не поддерживается сервером и не может быть обработан.
**502 Bad Gateway** — сервер, действуя как шлюз или прокси, получил недопустимый ответ от входящего сервера, к которому он обращался при попытке выполнить запрос.
**503 Service Unavailable** — сервер не готов обработать запрос (например, из-за технического обслуживания или перегрузки). Обратите внимание, что вместе с этим ответом должна быть отправлена ​​удобная страница с объяснением проблемы. Этот ответ следует использовать для временных условий, а HTTP-заголовок `Retry-After` по возможности должен содержать расчётное время до восстановления службы.
**504 Gateway Timeout** — этот ответ об ошибке выдается, когда сервер действует как шлюз и не может получить ответ за отведенное время.
**505 HTTP Version Not Supported** — версия HTTP, используемая в запросе, не поддерживается сервером.


### Часть 1. Из чего состоит HTTP запрос

Когда ваш браузер отправляет запрос на сервер, он посылает текстовое сообщение, которое строго структурировано. Оно состоит из 3-х частей:

**1. Стартовая строка (Request Line)**  
Это самая первая строка. Она обязательна и содержит три ключевых элемента:

- **Метод (HTTP Method):** Действие, которое вы хотите выполнить. Главные из них: `GET` (получить данные), `POST` (отправить новые данные), `PUT` (обновить данные целиком), `PATCH` (обновить часть данных), `DELETE` (удалить).
    
- **URI (Путь):** Адрес ресурса на сервере без домена. Например: `/catalog/shoes?id=5`.
    
- **Версия протокола:** Почти всегда сейчас это `HTTP/1.1` или `HTTP/2`.
    

> _Пример:_ `GET /index.html HTTP/1.1`

**2. Заголовки (Headers)**  
Это метаданные запроса — набор пар `Ключ: Значение`. Они описывают сам запрос, браузер и ожидания клиента. Самые важные:

- `Host: example.com` — **Обязательный заголовок**. Указывает, к какому именно сайту на сервере вы обращаетесь (виртуальный хостинг).
    
- `User-Agent: Mozilla/5.0...` — Информация о вашем браузере и ОС.
    
- `Accept: text/html` — Сообщает серверу, какой формат ответа вы ждете (html, json, xml, картинка).
    
- `Cookie: session=abc123` — Передает серверу сохраненные ранее данные (куки) для авторизации.
    
- `Content-Type: application/json` — Если вы что-то отправляете (POST), этот заголовок говорит, в каком формате отправлены данные.
    
- `Authorization: Bearer token...` — Токен для аутентификации.

**3. Тело (Body / Payload)**  
Это «груз» запроса. Присутствует не всегда (например, в `GET` запросах тела нет). Используется в `POST`, `PUT`, `PATCH` для передачи больших данных.

- Там может быть JSON `{"name": "Ivan", "age": 30}`.
    
- Данные формы (`key1=value1&key2=value2`).
    
- Или содержимое загружаемого файла (бинарные данные).

Это путь от нажатия клавиши Enter до загрузки страницы. Разделим его на сетевой уровень и уровень приложений.

#### Сетевой уровень (Инфраструктура)

1. **Ввод URL и разбор (Parsing):** Браузер определяет, что вы ввели: поисковый запрос или адрес сайта. Если адрес — он извлекает протокол (`https`), домен (`site.com`) и путь.
    
2. **DNS-резолвинг (Поиск IP):** Браузер проверяет кэш. Если IP адреса `site.com` нет в кэше, он отправляет запрос на DNS-сервер (обычно вашего провайдера или Google), чтобы узнать, по какому IP-адресу физически находится сервер.
    
3. **Установка TCP-соединения (3-way handshake):** Клиент и сервер «пожимают руки»:
    
    - Клиент: _«Привет (SYN)»_
        
    - Сервер: _«Привет, договорились (SYN-ACK)»_
        
    - Клиент: _«Ок, начинаем обмен (ACK)»_
        
4. **TLS Handshake (для HTTPS):** Если соединение защищенное, поверх TCP происходит обмен ключами шифрования. Стороны договариваются о симметричном ключе, которым будут шифровать все данные далее.
#### Уровень приложений (Логика запроса)

5. **Формирование запроса:** Браузер собирает «Стартовую строку» + «Заголовки» + «Тело» в один пакет (или несколько) и отправляет их серверу через установленное зашифрованное соединение.
    
6. **Обработка на сервере:**
    
    - Сервер (Nginx/Apache) принимает пакеты и читает заголовок `Host`, чтобы понять, какому сайту внутри сервера адресован запрос.
        
    - Веб-сервер передает запрос вашему приложению (PHP, Python, Java, Node.js).
        
    - Приложение читает путь (`/catalog/shoes`), проверяет права доступа, подключается к базе данных, выполняет сложную логику (например, достает товары из БД) и **генерирует ответ**.
        
7. **Формирование ответа (Response):** Сервер составляет ответ, который имеет такую же структуру, как и запрос (Стартовая строка с кодом статуса, Заголовки, Тело с HTML или JSON).
    
    - _Пример статусов:_ `200 OK` (все хорошо), `301 Moved` (редирект), `404 Not Found` (нет страницы), `500` (ошибка сервера).
        
8. **Передача ответа:** Сервер отправляет этот готовый HTML/JSON обратно клиенту по тому же TCP-каналу.
#### Клиентский уровень (Обработка в браузере)

9. **Получение и парсинг:** Браузер получает ответ, смотрит на `Content-Type` (тип контента) и код статуса.
    
    - Если код `301` — браузер читает заголовок `Location` и переходит по новому адресу (повторяя все этапы с начала).
        
    - Если `200` — начинает читать тело ответа.
        
10. **Отображение контента:** Браузер строит DOM-дерево (структуру страницы) из HTML, одновременно запрашивая дополнительные ресурсы, указанные в нем: CSS-стили, JS-скрипты, картинки и шрифты.
    

> **Важное уточнение:** Каждый ресурс (картинка, скрипт, шрифт) — это **новый HTTP запрос** к серверу (или кэшу браузера), который проходит все те же этапы (кроме DNS, если IP уже известен).

11. **Закрытие соединения (или Keep-Alive):** В HTTP/1.1 соединение может не закрываться сразу, а висеть в режиме `Keep-Alive` для отправки следующих запросов от браузера (например, для загрузки картинок), чтобы не тратить время на повторное TCP рукопожатие. В HTTP/2 и HTTP/3 соединение вообще мультиплексное (отправляет много запросов параллельно по одному каналу).
#### HTTP1 -> HTTP2

Первая версия протокола http требовала дожидаться получения ответа перед отправлением следующего запроса в рамках одного соединения. Во второй версии протокола - это исправили, соединение может использоваться без ожидания завершения уже отправленного запроса.
#### HTTP2 -> HTTP3/QUIC

Проблема блокировки была решена в версии 2 — но только на уровне http протокола. На транспортном уровне **tcp** она все еще есть в виде обязательного **последовательного** получения пакетов. Поэтому версию 3 собрали на протоколе **udp**, в которой этой особенности нет, и назвали это QUIC.

### Блок 1. «На внимательность» (Нюансы протокола)

**1. Можно ли отправить тело (Body) в GET-запросе?**

- **Каверзность:** 90% джунов скажут «Нет!». На самом деле спецификация **не запрещает** тело в GET, но серверы и прокси имеют право его проигнорировать или сбросить соединение.
    
- **Как ответить:** _«Технически — да, но так делать нельзя, потому что это нарушает идемпотентность и семантику REST. Большинство серверов (Nginx/Apache) просто не читают тело GET, поэтому данные туда класть бесполезно. Для данных всегда используем POST/PUT»._
    

**2. В чем принципиальная разница между `PUT` и `PATCH`?**

- **Каверзность:** Многие отвечают: «PUT обновляет полностью, PATCH — частично». Это верно, но неполно.
    
- **Как ответить:** _«PUT требует, чтобы клиент прислал **полный** объект целиком (заменяя его на сервере). Если ты отправишь только одно поле, остальные затрутся дефолтными значениями или null-ами. PATCH же принимает список операций (например, по стандарту JSON Patch) и меняет только то, что указано. Также PUT идемпотентен (повторный запрос дает тот же результат), а PATCH — не обязательно»._

### Блок 2. «Сетевой» (То, что лежит глубже HTTP)

**3. Почему соединение по HTTPS устанавливается дольше, чем по HTTP, даже если скорость канала одинаковая?**

- **Каверзность:** Ответ «потому что шифрует данные» — слишком поверхностный.
    
- **Как ответить:** _«Замедление происходит из-за дополнительных **RTT (Round Trip Time)**. Для HTTP нужно 3 рукопожатия TCP (1.5 RTT). Для HTTPS добавляется TLS Handshake, который требует еще 2-х RTT (в TLS 1.2) для обмена ключами и проверки сертификата. Итого вместо 1.5 RTT мы тратим ~4 RTT до отправки первого байта данных. Именно поэтому все переходят на TLS 1.3 (где рукопожатие занимает 1 RTT) и HTTP/3 (QUIC)»._
    

**4. Что такое `Keep-Alive` и почему он может навредить?**

- **Каверзность:** Обычно говорят, что Keep-Alive — это хорошо (экономит время на TCP рукопожатиях).
    
- **Как ответить:** _«Keep-Alive переиспользует одно TCP-соединение для нескольких запросов. Это хорошо, но на высоконагруженных проектах это может привести к **голоданию соединений (starvation)**, если клиенты висят и не закрывают сокеты. Сервер держит тысячи открытых соединений, тратит память и достигает лимита файловых дескрипторов. Поэтому мы всегда балансируем таймауты (например, ставим `keepalive_timeout` не больше 60 секунд)»._

### Блок 3. «Безопасность» (Ловушки для тех, кто пишет код)

**5. Чем отличается `Authentication` от `Authorization` и как это работает в HTTP?**

- **Каверзность:** Часто путают эти термины.
    
- **Как ответить:** _«Authentication (Аутентификация) — это "ты кто?" (проверка логина/пароля). Authorization (Авторизация) — это "что тебе можно?" (проверка прав доступа). В HTTP аутентификация часто происходит через базовый `Authorization: Basic base64...` (который опасен без HTTPS) или через Bearer JWT-токен. При этом заголовок называется Authorization, хотя по факту там лежит токен для аутентификации — это исторический костыль спецификации»._
    

**6. Как защититься от CSRF (Cross-Site Request Forgery), если ты используешь JWT-токены в `localStorage`?**

- **Каверзность:** Многие думают, что JWT сам по себе — защита.
    
- **Как ответить:** _«JWT в localStorage уязвим для XSS-атак (злоумышленник украдет токен через внедренный скрипт). Лучший вариант — хранить токен в **HttpOnly Cookie** (тогда скрипты его не читают). Но тогда он автоматически отправляется браузером, что делает нас уязвимыми для CSRF. Решение: использовать **Double Submit Cookies** (отправлять токен и в куке, и в отдельном заголовке `X-CSRF-Token`, сравнивая их на сервере) или использовать параметр `SameSite: Strict/Lax`»._

### Блок 4. «Кэширование» (Самая частая причина багов)

**7. Почему запрос с `Cache-Control: no-cache` все равно может вернуть старые данные из кэша браузера?**

- **Каверзность:** Буквальный перевод «no-cache» вводит в заблуждение.
    
- **Как ответить:** _«Потому что `no-cache` означает не "не кэшируй", а "**перепроверь** валидность у сервера перед выдачей" (revalidate). Если сервер ответит `304 Not Modified`, браузер все равно покажет старую копию. Чтобы реально запретить кэширование, нужно использовать комбинацию `Cache-Control: no-store, must-revalidate` и добавить уникальный параметр (query string) к URL, чтобы обойти кэш на уровне прокси»._
    

**8. Чем отличается код ответа `301` от `308`?**

- **Каверзность:** Все знают про 301 (навсегда). А 308 появился недавно.
    
- **Как ответить:** _«Оба означают постоянный редирект. Но `301` разрешает браузеру и поисковикам менять метод запроса (например, POST может стать GET). А `308` (Permanent Redirect) **строго запрещает** менять метод и тело запроса при перенаправлении. То есть, если ты отправил POST на адрес А, а сервер вернул 308, браузер обязан отправить POST на адрес Б, сохранив всё тело»._
### Блок 5. «Бонусный удар» (На знание современных протоколов)

**9. В чем магия HTTP/3? Почему он быстрее, если по сути это тот же HTTPS?**

- **Каверзность:** Ответ «он быстрее» — не засчитывается.
    
- **Как ответить:** _«HTTP/3 работает поверх **QUIC**, который использует **UDP**, а не TCP. Это решает проблему "Head-of-Line blocking" (блокировки очереди) на транспортном уровне. Если в HTTP/2 теряется один пакет TCP — вся очередь запросов останавливается, пока его не досылают. В HTTP/3 потеря одного пакета влияет только на один конкретный поток (стрим), остальные продолжают качаться независимо. Плюс QUIC сокращает время установки соединения до 0-1 RTT»._
    

**10. Если клиент отправил запрос и разорвал соединение (закрыл вкладку), а сервер все еще считает данные из БД — что произойдет?**

- **Каверзность:** Проверка знания бэкенд-архитектуры.
    
- **Как ответить:** _«Если мы говорим о синхронном блокирующем коде (например, PHP-FPM) — процесс останется висеть, пока не отработает скрипт и не попытается отправить ответ в закрытый сокет (что вызовет предупреждение, но процесс завершится). Если мы говорим про асинхронный код (Node.js, Python asyncio) — сервер узнает о разрыве по событию `close`, может отправить сигнал отмены (`AbortSignal` в fetch API) в бэкенд, и мы должны прервать тяжелый запрос к БД, чтобы не тратить ресурсы CPU впустую (это feature под названием Request Cancellation)»._
