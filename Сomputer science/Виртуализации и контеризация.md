### 1. Виртуализация

**Виртуальная машина эмулирует/виртуализирует целую аппаратную среду**, поэтому внутри неё запускается полноценная гостевая ОС со своим kernel.

Схематично:

```
Application
    ↓
Guest OS
    ↓
Guest Kernel
    ↓
Virtual Hardware
    ↓
Hypervisor
    ↓
Host OS / Hardware
```

Например, запускаем Linux VM на Linux/Windows. Внутри VM есть собственный Linux kernel.
*Слово **kernel** (в переводе с английского — «ядро») чаще всего оз==начает главную часть операционной системы, которая управляет процессором, памятью и устройствами==.

Главное:

> **VM виртуализирует аппаратные ресурсы и запускает отдельное ядро ОС.**

Поэтому VM обычно требует больше памяти, места и времени на запуск.

### 2. Контейнеризация

Контейнер **не содержит отдельную полноценную ОС и отдельное ядро**. Контейнер использует kernel хост-системы.

Схематично:

```
Container A       Container B
     ↓                 ↓
 Application       Application
     ↓                 ↓
     └──── Container Runtime ────┐
                                 ↓
                              Host Kernel
                                 ↓
                              Hardware
```

Например:

```
docker run ubuntu
```

не означает, что внутри Docker-контейнера запустился полноценный Ubuntu kernel.

Там есть user-space Ubuntu: `/bin`, библиотеки, утилиты и т.д., но **kernel берётся от host OS**.

В Linux Docker использует механизмы ядра вроде:

- namespaces — изоляция процессов, сети, mount points и т.д.;
- cgroups — ограничение и учёт CPU, RAM и других ресурсов;
- capabilities — ограничение привилегий;
- seccomp — фильтрация системных вызовов.

## А теперь самое интересное — syscall

Вот здесь, скорее всего, и был основной смысл вопроса.

Приложение не может напрямую обращаться к железу.

Например:

```
file, _ := os.Open("test.txt")
```

В конечном итоге работа с файлом приводит к системным вызовам ядра.

Упрощённо:

```
Go application
      ↓
   libc / runtime
      ↓
    syscall
      ↓
 Linux Kernel
      ↓
   filesystem
      ↓
    disk
```

**System call — это интерфейс между user space и kernel space.**

Например:

```
read()
write()
openat()
mmap()
clone()
socket()
```

# 4. Что происходит с syscall в VM?

В классической виртуализации:

```
Application
    ↓
Guest syscall
    ↓
Guest Kernel
    ↓
Virtual Hardware
    ↓
Hypervisor
    ↓
Real Hardware
```

Очень важный момент:

**обычный syscall приложения не обязательно "транслируется" гипервизором.**

Если приложение внутри Linux VM делает:

```
read()
```

оно обращается к **guest kernel**.

Guest kernel уже работает с виртуальным оборудованием, а гипервизор виртуализирует доступ к физическим ресурсам.

Современные CPU поддерживают аппаратную виртуализацию, например Intel VT-x / AMD-V, поэтому выполнение большого количества guest-кода происходит практически напрямую на CPU, а не через постоянную программную эмуляцию.

# 5. А что происходит в контейнере?

Вот здесь интереснее:

```
Application
     ↓
 syscall
     ↓
Host Kernel
     ↓
Hardware
```

**Нет отдельного container kernel.**

Например, контейнер вызывает:

```
socket()
```

syscall фактически обрабатывается **ядром хостовой Linux-системы**.

А namespace определяет, **какие ресурсы этого kernel контейнеру видны**.

Например:

```
Container A
PID namespace
   ↓
видит свои процессы

Container B
PID namespace
   ↓
видит другие процессы
```

При этом kernel один и тот же.

# 6. А что значит «трансляция syscall»?

**Контейнеризация vs виртуализация и трансляция системных вызовов**:

> В обычном Linux-контейнере трансляции syscall нет в смысле преобразования syscall контейнера в syscall другого ядра. Контейнер использует kernel хост-системы. Изоляция достигается namespaces, cgroups и другими механизмами kernel.

А вот **трансляция/перехват системных вызовов действительно может присутствовать** в некоторых технологиях.

Например, когда пытаются запускать приложения одной ОС поверх другой.

Классический пример:

```
Windows application
        ↓
Windows API / syscall
        ↓
compatibility layer
        ↓
Linux
```

Например, **Wine** реализует Windows API поверх Linux, то есть это уже другой механизм, не обычная контейнеризация.
