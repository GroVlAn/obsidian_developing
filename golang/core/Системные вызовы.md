Отличный вопрос! Давайте разберемся, как это работает на самом деле на низком уровне. Вы почти правильно помните, но есть важные нюансы.

## Ключевое различие: файлы vs сеть

### 1. Файловые операции (синхронные системные вызовы)

**Проблема:** Файловые операции в большинстве ОС не поддерживают асинхронный режим (кроме специфических API вроде io_uring в Linux).

**Как Go решает эту проблему:**

1. **Создание отдельного потока:**
    
    - Когда goroutine выполняет файловую операцию (например, `os.ReadFile`)
        
    - Go runtime определяет, что это блокирующий системный вызов
        
    - Создается **новый OS thread** (или используется из пула)
        
    - Goroutine "прикрепляется" к этому потоку
        
    - Системный вызов выполняется на этом отдельном потоке
        
2. **Что происходит с основным потоком:**
    
    - Основной OS thread, на котором работал планировщик Go, **освобождается**
        
    - Планировщик может использовать его для других goroutines
        
    - Это позволяет другим goroutines продолжать работу
        
3. **После завершения операции:**
    
    - Goroutine "открепляется" от вспомогательного потока
        
    - Возвращается в очередь планировщика
        
    - Вспомогательный поток возвращается в пул или уничтожается
        

text

Goroutine A ──> файловая операция ──> создается новый OS thread
     │                                    │
     │                                    ├──> системный вызов read()
     │                                    │
Goroutine B ──> продолжает работу ──> на основном потоке
     │                                    │
     │                                    ├──> операция завершена
     │                                    │
Goroutine A ──> возвращается в планировщик

### 2. Сетевые операции (асинхронные)

**Как работает netpoller:**

1. **Инициализация:**
    
    - При старте Go runtime создает **netpoller** - специальный компонент
        
    - Netpoller использует асинхронные API ОС:
        
        - Linux: epoll
            
        - macOS/BSD: kqueue
            
        - Windows: IOCP (I/O Completion Ports)
            
2. **При сетевой операции:**
    
    - Goroutine выполняет, например, `conn.Read()`
        
    - Вместо блокирующего системного вызова, запрос регистрируется в netpoller
        
    - Goroutine **переводится в состояние waiting** и открепляется от потока
        
    - OS thread освобождается для других goroutines
        
3. **Ожидание данных:**
    
    - Netpoller опрашивает ОС через epoll/kqueue/IOCP
        
    - Когда данные готовы, netpoller получает уведомление
        
    - Соответствующая goroutine переводится в состояние runnable
        
    - Планировщик назначает её на свободный OS thread
        

text

Goroutine A ──> conn.Read() ──> регистрация в netpoller
     │                              │
     │                              ├──> goroutine A → waiting
     │                              │
Goroutine B ──> продолжает работу ──> на освободившемся потоке
     │                              │
     │                              ├──> данные получены (epoll)
     │                              │
Goroutine A ──> возвращается в runnable ──> выполняется на любом потоке

## Почему такое различие?

### Файлы:

- Файловые дескрипторы **всегда готовы** для чтения/записи с точки зрения epoll
    
- Операции с диском имеют непредсказуемую задержку (механические диски, кэш)
    
- Большинство ОС не предоставляют асинхронный API для обычных файлов
    
- Поэтому Go вынужден использовать **блокирующие вызовы в отдельных потоках**
    

### Сеть:

- Сетевые операции имеют **естественный асинхронный характер**
    
- ОС предоставляют мощные API для асинхронной работы (epoll, kqueue, IOCP)
    
- Можно эффективно обрабатывать тысячи соединений с минимальным числом потоков
